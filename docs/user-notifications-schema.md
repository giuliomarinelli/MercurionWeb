# User notifications PostgreSQL schema

**Reference Trello card:** `6abfc9a4c1919d7ad547b3e9`  
**Reference branch:** `feature/6abfc9a4c1919d7ad547b3e9-notifications`  
**Application entity:** `MercurionWebNode/src/app_modules/notification/models/entities/user-notification.entity.ts`

This schema is externally managed, in accordance with `docs/database-schema.md`.
It is **not** a TypeORM migration and must not be wired to application startup.

The application must fail rather than silently creating or repairing this schema when the table is missing or incompatible.

## Apply

Target: PostgreSQL 16. Notification UUIDv7 identifiers are generated by the application with `@kripod/uuidv7` before insertion.

```sql
BEGIN;

CREATE SEQUENCE user_notifications_revision_seq AS BIGINT;

CREATE TABLE user_notifications (
    id UUID PRIMARY KEY,
    recipient_user_id UUID NOT NULL,

    type VARCHAR(120) NOT NULL,
    version INTEGER NOT NULL,
    category VARCHAR(60) NOT NULL,

    title VARCHAR(180) NOT NULL,
    summary VARCHAR(400) NOT NULL,
    body TEXT NOT NULL,
    payload JSONB NOT NULL DEFAULT '{}'::jsonb,

    resource_type VARCHAR(100),
    resource_id VARCHAR(180),

    created_at BIGINT NOT NULL,
    updated_at BIGINT NOT NULL,

    seen_at BIGINT,
    read_at BIGINT,
    dismissed_at BIGINT,

    revision BIGINT NOT NULL,
    created_revision BIGINT NOT NULL,

    dedupe_key VARCHAR(255) NOT NULL,

    CONSTRAINT ck_user_notifications_version_positive
        CHECK (version > 0),

    CONSTRAINT fk_user_notifications_recipient
        FOREIGN KEY (recipient_user_id)
        REFERENCES users(id)
        ON DELETE CASCADE,

    CONSTRAINT uq_user_notifications_dedupe
        UNIQUE (dedupe_key)
);

CREATE OR REPLACE FUNCTION assign_user_notification_revision()
RETURNS trigger
LANGUAGE plpgsql
AS $$
DECLARE
    next_revision BIGINT;
    now_ms BIGINT;
BEGIN
    next_revision := nextval('user_notifications_revision_seq');
    now_ms := FLOOR(EXTRACT(EPOCH FROM clock_timestamp()) * 1000)::BIGINT;

    NEW.revision := next_revision;

    IF TG_OP = 'INSERT' THEN
        NEW.created_revision := next_revision;
        NEW.created_at := now_ms;
    END IF;

    NEW.updated_at := now_ms;

    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_user_notifications_revision
BEFORE INSERT OR UPDATE
ON user_notifications
FOR EACH ROW
EXECUTE FUNCTION assign_user_notification_revision();

CREATE INDEX idx_user_notifications_recovery
    ON user_notifications (recipient_user_id, revision);

CREATE INDEX idx_user_notifications_active_recent
    ON user_notifications (recipient_user_id, created_at DESC, id DESC)
    WHERE dismissed_at IS NULL;

CREATE INDEX idx_user_notifications_active_unread
    ON user_notifications (recipient_user_id, created_at DESC, id DESC)
    WHERE dismissed_at IS NULL
      AND read_at IS NULL;

CREATE INDEX idx_user_notifications_active_unseen
    ON user_notifications (recipient_user_id, created_at DESC, id DESC)
    WHERE dismissed_at IS NULL
      AND seen_at IS NULL;

COMMIT;
```

## Ownership rules

The database owns these values:

- `created_at`;
- `updated_at`;
- `revision`;
- `created_revision`.

Every insert and every update consumes a new value from
`user_notifications_revision_seq`. On insert, `created_revision` is set to
the same value as the initial `revision` and is never changed afterwards.

This is intentional: the recovery cursor must be ordered by PostgreSQL itself,
including writes produced by processes other than MercurionWebNode.

The application owns notification `id` generation and supplies a UUIDv7 before insertion. PostgreSQL persists the UUID value and does not generate notification identifiers.

## Development smoke check

With a valid existing user ID:

```sql
INSERT INTO user_notifications (
    id,
    recipient_user_id,
    type,
    version,
    category,
    title,
    summary,
    body,
    dedupe_key
)
VALUES (
    '<NOTIFICATION_UUIDV7>',
    '<USER_UUID>',
    'security.password_changed',
    1,
    'security',
    'Password modificata',
    'Test notification',
    'Test notification body',
    'dev-smoke:user-notification'
)
RETURNING
    id,
    created_at,
    updated_at,
    revision,
    created_revision;
```

For a newly inserted row:

- `revision = created_revision`;
- `created_at` and `updated_at` are populated;
- repeating the same `dedupe_key` fails at the database boundary.

Delete the smoke row afterwards:

```sql
DELETE FROM user_notifications
WHERE dedupe_key = 'dev-smoke:user-notification';
```

## Rollback for a disposable development environment

This is not an application migration. Use only when intentionally removing the
feature schema from a disposable environment.

```sql
BEGIN;

DROP TABLE IF EXISTS user_notifications;
DROP FUNCTION IF EXISTS assign_user_notification_revision();
DROP SEQUENCE IF EXISTS user_notifications_revision_seq;

COMMIT;
```
