# 0001 - Canonicalize REST contract ownership

- [ ] DONE
- [ ] BLOCKED

## Objective

Eliminate manually duplicated Angular REST wire definitions so every public
request/response shape derives from a versioned framework-neutral shared
package, while retaining checked Nest validation adapters where runtime
validation or transformation requires them.

Create the repository-root npm workspace containing `MercurionWebNg`,
`MercurionWebNode`, and shared packages; establish one reproducible root
dependency topology; and preserve the already-green permanent CI baseline
through that migration.

Source: `SYS-001` in Series `0001`.

## Context

The audit found REST DTOs duplicated between
`MercurionWebNg/src/app/Models/**` and Nest DTOs under
`MercurionWebNode/src/**/Models/DTO/**`. Angular services using `HttpClient`
include auth, account, feedback, history, country, recovery, Mercurion AI, and
RDKit clients.

Repository-wide baseline construction and CI bootstrap are no longer part of
this recipe. They are the external session prerequisite documented in
`docs/autonomous-development/CI-BASELINE.md`. Task `0001` starts only from a
clean `develop` whose exact SHA is already green on permanent Windows/Linux
GitHub Actions.

## Relevant files and modules

- `MercurionWebNg/src/app/Models/`
- Angular REST client services under `MercurionWebNg/src/app/services/`
- `MercurionWebNode/src/**/Models/DTO/`
- Nest REST controllers, serializers, and boundary mappers
- root and project package manifests and lockfiles
- `packages/rest-contracts/`
- deterministic contract/parity checks
- `.github/workflows/ci.yml`, only as required to preserve CI across the
  workspace-topology migration

## In scope

- Inventory public REST request/response payloads consumed by Angular.
- Establish one versioned, framework-neutral shared contract package.
- Replace manual client-side wire-shape copies with shared types.
- Retain Nest-only decorated validation/transformation DTOs as checked boundary
  adapters where required.
- Add deterministic compile-time and/or runtime contract-parity checks.
- Create a root npm workspace for Angular, Nest, and shared packages.
- Replace the Angular/Nest split install topology with one reproducible root
  lockfile and install flow.
- Adapt the permanent workflow to the root topology without removing its
  Windows/Linux matrix, feature-branch trigger, `develop` trigger, or stable
  aggregate gate.

## Out of scope

- Constructing or repairing the repository-wide CI baseline.
- Absorbing unrelated lint, type, test, build, or dependency debt.
- GraphQL and WebSocket contracts.
- Unrelated API redesigns or endpoint renames.
- Changes to `../MercurionTox21`.
- Disabling, weakening, or bypassing an existing CI gate.

## Decisions already made

- The permanent green baseline is established outside the numbered workload.
- The canonical REST source is a versioned, framework-neutral shared package.
- Angular never imports Nest transport classes or depends on
  `class-validator`, `class-transformer`, or another Nest runtime concern.
- Decorated Nest DTO classes may remain at the HTTP boundary when required.
  They are adapters, not an independently evolving canonical contract.
- Deduplication is incremental and non-breaking.
- Existing externally visible REST behaviour is preserved unless another task
  explicitly changes it.
- Root lockfiles are generated by pinned npm from a clean dependency tree and
  are never manually edited.

## Requirements

1. Enumerate Angular `HttpClient` calls and the Nest endpoints they consume.
2. Identify duplicated request/response types.
3. Separate portable wire semantics from Nest validation/transformation
   concerns.
4. Define every public REST wire payload in the shared package without Angular
   or Nest runtime dependencies.
5. Migrate Angular consumers to shared types.
6. Keep Nest as the runtime validator and constrain retained adapters to the
   shared contract.
7. Add deterministic checks that fail when clients, adapters, serializers, or
   mappers drift.
8. Preserve current validation, transformation, serialization, and JSON shape.
9. Establish the root workspace and one reproducible lockfile/install flow.
10. Preserve the complete permanent CI contract throughout the migration.

## Acceptance criteria

- [ ] Every public REST payload consumed by Angular has one canonical shared
  wire definition.
- [ ] Angular has no handwritten duplicate of a migrated wire DTO.
- [ ] Angular has no Nest or validation-framework runtime dependency.
- [ ] Necessary Nest decorated DTOs are checked boundary adapters.
- [ ] Existing REST validation, transformation, serialization, and JSON shapes

- [ ] Contract-parity checks are deterministic and pass twice without changing

- [ ] The root workspace clean-install flow is reproducible.
- [ ] CI still runs on Windows and Ubuntu for feature branches and `develop`.
- [ ] The exact final feature SHA passes the permanent remote CI before merge.
- [ ] The complete local and remote CI-parity gates pass without unrelated
  baseline remediation.

## Validation

At task start, run the package-local baseline from
`docs/autonomous-development/CI-BASELINE.md`. It must already be green; a
failure is not permission to repair unrelated repository debt inside SYS-001.

After the workspace migration, generate the root lockfile only through a clean
install using the pinned toolchain. Run the root contract checks twice, the
complete lint/type/test/E2E/build suite, and verify the second run leaves the
tree unchanged. Push the feature SHA and require its Windows/Linux GitHub
Actions workflow to succeed before integration.

Task `0008` later completes the stable root `npm ci` plus `npm run ci:check`
interface and expands the gate registry; it must not recreate a missing CI
control plane.

## Browser validation

Not applicable. Contract ownership and compatibility are established through
compile-time checks, contract tests, service/controller tests, and CI.

## Stop conditions

Mark `BLOCKED` if a payload cannot be migrated without an unauthorized public
API change, if a Nest runtime validation adapter cannot be kept compatible, if
the workspace migration cannot reproduce installs on both CI platforms, or if
the exact feature-SHA workflow does not succeed.

An unrelated failure already present on the starting `develop` baseline is a
session-level invariant violation and must not be assigned to this task.

## Dependencies

- None. The permanent exact-SHA green baseline is a session launch invariant,
  not a numbered task dependency.

## Implementation notes

Prefer a non-breaking migration. Share portable transport semantics without
forcing framework-specific classes into the common package. Preserve the
permanent workflow while adapting its install commands to the new root
workspace.
